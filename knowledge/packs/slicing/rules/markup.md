# Markup — Universal Slicing Rules

These rules apply to every Slicing command that turns a Figma design into HTML, SCSS, Tailwind and
JavaScript: `/figma-to-block-html` and any future Slicing command.

Read this file before generating any HTML, SCSS, JS or config file from a Figma design.
File locations are defined in `knowledge/slicing/rules/structure.md`.

---

## 1. Never write Tailwind utilities in HTML

All visual styling lives in SCSS. HTML uses semantic BEM class names only.

**Wrong:**
```html
<section class="flex flex-col md:flex-row gap-6 py-12 bg-brand-primary">
```

**Correct:**
```html
<section class="hero-block">
```

```scss
.hero-block {
  @apply flex flex-col gap-6 py-12 bg-brand-primary;

  @screen md {
    @apply flex-row;
  }
}
```

Exception: `container` on the `__inner` element (see Rule 8).

---

## 2. One SCSS partial per component or block

Every block and every component gets its own SCSS partial. Every generated partial must be imported
in the main SCSS entry file. Paths: `knowledge/slicing/rules/structure.md`.

---

## 3. BEM naming

```
.block-name               ← block
.block-name__element      ← element
.block-name--modifier     ← modifier
```

Use kebab-case. Match the Figma layer name converted to kebab-case:
`HeroBlock` → `.hero-block`, `CTA Button` → `.hero-block__cta-button`.

---

## 4. Mobile-first responsive

Base classes = mobile. Larger breakpoints use Tailwind screen directives inside the SCSS rule:

```scss
.hero-block {
  @apply flex flex-col gap-4 py-8 px-4;    // mobile

  @screen md {
    @apply flex-row gap-12 py-24 px-16;   // desktop
  }
}
```

Always generate responsive styles — even if only a desktop frame was provided in Figma. Use the
smart mobile defaults from the command skill when no mobile frame exists.

---

## 5. Use design token names, not raw values

Reference token names from `.wpaikit/design-system.json` (or the Figma Variables when the file does
not exist). Never hardcode hex values or raw px.

```scss
// Wrong
color: #0f172a;
padding: 48px;

// Correct
@apply text-primary py-12;
```

Token → Tailwind class mapping:
- `Colors/brand/primary` → `brand-primary`
- `Colors/text/primary` → `text-primary`
- `Colors/bg/canvas` → `bg-canvas`
- `Spacing/N` → Tailwind spacing scale (`Spacing/4` → `p-4`, `gap-4`, …)
- `Radius/lg` → `rounded-lg`
- `Heading/4xl` → `text-4xl`

---

## 6. Variant classes as BEM modifiers

Map each component variant (type, size, state) to a BEM modifier:

```scss
.btn {
  @apply inline-flex items-center font-medium transition-colors;

  &--primary   { @apply bg-brand-primary text-inverse; }
  &--secondary { @apply bg-brand-accent text-inverse; }
  &--sm        { @apply text-sm px-3 py-1.5 rounded-md; }
  &--disabled  { @apply opacity-40 pointer-events-none; }
}
```

```html
<a class="btn btn--primary btn--sm" href="#">Get started</a>
```

---

## 7. File header comment

Every generated HTML file starts with:

```html
<!--
  Block: HeroBlock
  Content fields: heading, description, cta (link), background_image (image), items[] (title, image)
  Generated by /figma-to-block-html
-->
```

The `Content fields` line documents the content model taken from the Figma layer names
(`knowledge/shared/rules/figma-blocks.md`). It lets any later integration (CMS, framework, backend)
map the static markup to real data without re-reading Figma.

Every generated SCSS partial starts with:

```scss
// Block: HeroBlock
// Generated by /figma-to-block-html
```

Every generated JS module starts with:

```js
// Block: HeroBlock — accordion behaviour
// Generated by /figma-to-block-html
```

---

## 8. Container pattern for blocks

```html
<section class="hero-block">
  <div class="hero-block__inner container">
    <div class="hero-block__content">...</div>
  </div>
</section>
```

```scss
.hero-block {
  @apply py-8;         // vertical padding + background only — no px

  @screen md {
    @apply py-24;
  }

  &__inner { }         // intentionally empty — container handles width/centering
}
```

- `section` = vertical padding (`py-*`) + background only — never `px-*`
- `__inner container` = width constraint and centering via Tailwind `container`
- Full-width blocks (edge-to-edge images, maps) skip the `__inner container` wrapper

---

## 9. Semantic, accessible HTML

- One `<section>` (or `<header>`, `<footer>`, `<nav>`) root element per block
- Heading levels follow the page outline; never skip levels inside a block
- Links are `<a href>`, actions are `<button type="button">`
- Every `<img>` has `alt` (empty `alt=""` only for decorative `Decoration/*` layers),
  `width`, `height` and `loading="lazy"` (except the first visible hero image)
- Text comes from the Figma layer — do not invent copy; use the design's real text as content
- Images are referenced from the assets directory, never inlined as base64

---

## 10. JavaScript only for behaviour

- Generate JS only when the block has interactive behaviour (slider, tabs, accordion, modal,
  menu toggle). Static blocks get no JS file.
- Vanilla ES modules, no framework unless `.wpaikit/project.md` lists one in the tech stack
- One module per block, exporting `init{BlockPascal}()`; it finds every `.block-name` root and
  initialises each instance independently
- Behaviour hooks use `data-*` attributes (`data-accordion-trigger`), never styling classes
- State is reflected with ARIA attributes (`aria-expanded`, `aria-hidden`) and BEM modifiers
  (`.faq-block__item--open`), not inline styles
- Every module is imported and initialised from the main JS entry file

---

## 11. Per-file validation loop

Every generated or modified file goes through this loop before moving to the next file:

```
1. Write the file
2. Validate against the checklist below
3. Fix all violations found
4. Re-validate — only proceed when all checks pass
```

### HTML checklist

- [ ] Header comment present with `Content fields`
- [ ] No Tailwind utility classes in `class=""` — only BEM class names (exception: `container`)
- [ ] Semantic root element, correct heading levels
- [ ] Every image has `alt`, `width`, `height`
- [ ] Known components from `.wpaikit/components-registry.md` reuse their existing markup and classes
- [ ] No inline styles, no inline scripts

### SCSS checklist

- [ ] Header comment present
- [ ] All class names are BEM kebab-case
- [ ] Tailwind only through `@apply` / `@screen`
- [ ] No hardcoded hex colors anywhere
- [ ] If a color has no matching entry in `tailwind.config.js`:
  1. Stop and ask: `Color #xxxxxx not found in tailwind.config.js. Add as [proposed-name]? [yes / rename / skip]`
  2. On `yes` or `rename` → add to `theme.extend.colors` and to `design-system.json → colors` (if the file exists)
  3. On `skip` → use the closest existing token, note the substitution
  4. Never leave a raw hex in the output
- [ ] Mobile-first: base = mobile, `@screen md {}` = desktop
- [ ] No `px-*` on the outer `section` when the container is used
- [ ] Partial is imported in the main SCSS entry file

### JS checklist (only when a JS file was generated)

- [ ] Header comment present
- [ ] Exports `init{BlockPascal}()`, supports multiple instances on the page
- [ ] Hooks via `data-*`, state via ARIA + BEM modifiers
- [ ] Keyboard accessible (Enter/Space on triggers, Escape closes overlays)
- [ ] Imported and initialised in the main JS entry file
